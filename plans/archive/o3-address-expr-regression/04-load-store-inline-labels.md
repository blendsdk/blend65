# Load-Store Elimination Through Inline Labels

> **Document**: 04-load-store-inline-labels.md
> **Parent**: [Index](00-index.md)

## Overview

Extend `loadStoreElimination` to handle STORE/LOAD pairs separated by inline continuation labels. Currently it only handles **consecutive** pairs. After inlining, inline continuation labels often sit between a STORE and its immediately-following LOAD, preventing elimination.

This is a general improvement that benefits ALL optimization levels where inlining occurs, not just the O3 address-expr regression.

## The Problem

Currently `loadStoreElimination` handles:
```
STORE_WORD x; LOAD_WORD x  (consecutive) → remove LOAD_WORD
STORE_BYTE x; LOAD_BYTE x  (consecutive) → remove LOAD_BYTE
```

But after inlining, the inline continuation label can sit between them:
```
STORE_WORD x                       ← stores to param slot
LABEL _inline_callee_N_cont        ← inline continuation (sequencing only)
LOAD_WORD x                        ← callee body reads param
```

The LABEL prevents the consecutive-pair check from matching.

## The Fix

### Extend Patterns for Inline-Label Gap

Add new patterns to `loadStoreElimination`:

**Pattern: STORE_WORD x; LABEL _inline_*_cont; LOAD_WORD x → remove LOAD_WORD**
```typescript
// Pattern: STORE_WORD x; LABEL _inline_*_cont; LOAD_WORD x
// The value is still in A:X after the STORE, and the inline label
// is a sequencing marker (no external code jumps to it), so
// the subsequent LOAD is redundant.
if (i + 2 < instructions.length) {
  const instr = instructions[i];
  const mid = instructions[i + 1];
  const next = instructions[i + 2];

  if (
    instr.opcode === ILOpcode.STORE_WORD &&
    mid.opcode === ILOpcode.LABEL &&
    isInlineContinuationLabel(mid) &&
    next.opcode === ILOpcode.LOAD_WORD
  ) {
    const storeSlot = this.getSlotName(instr);
    const loadSlot = this.getSlotName(next);
    if (storeSlot && loadSlot && storeSlot === loadSlot) {
      toRemove.add(i + 2); // Remove the LOAD_WORD
    }
  }
}
```

**Pattern: STORE_BYTE x; LABEL _inline_*_cont; LOAD_BYTE x → remove LOAD_BYTE**

Same logic but for byte-width operations.

### Safety Consideration

Inline continuation labels are **sequencing-only markers** generated by the function inliner. The `isInlineContinuationLabel()` guard (from `il/guards.ts`) checks for the `_inline_*_cont` naming pattern. No external control flow targets these labels (after `redundantJumpElimination` has removed the JUMP-to-next-instruction pattern).

However, if the inlined function has **multiple return paths**, there could be a JUMP targeting this label from within the inlined body. In that case, execution arriving via the JUMP would NOT have the STORE's value in A:X — it would come from a different path.

**Mitigation**: This pattern is safe ONLY because:
1. The STORE immediately precedes the LABEL
2. If execution reaches STORE, it falls through to LABEL, and A:X still holds the stored value
3. If execution JUMPs to the LABEL from elsewhere, the LOAD is needed
4. We check that STORE is at `[i]`, LABEL at `[i+1]`, LOAD at `[i+2]` — ensuring the STORE dominates the LABEL+LOAD in the fallthrough path

**Conservative approach**: Only apply when STORE is **immediately** before the LABEL. Do not apply if there are intervening instructions.

### Import Required

```typescript
import { isInlineContinuationLabel } from '../../il/guards.js';
```

This import already exists in the file (added in optimization-pass2 Phase 4 for const-prop/copy-prop).

## Expected Impact

- Cleaner IL after inlining at all levels where inlining occurs
- Reduces the number of redundant LOAD instructions
- Works synergistically with the store-gap pattern fix (Phase 1) — when this elimination runs first, it removes the LOAD_WORD, and the dead STORE_WORD is then caught by the store-gap pattern
- Future-proofs against similar pattern-breaking interactions
