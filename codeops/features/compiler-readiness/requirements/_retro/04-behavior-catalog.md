## Language Processing

### LANG-01: Programs are lexed, parsed and semantically analyzed

**Statement:** A developer can submit Blend65 modules and receive a typed semantic model or
structured diagnostics.
**Evidence:** frontend public API and extensive specification tests.
**Confidence:** ✅ Confirmed.

### LANG-02: Valid programs lower through IL to 6502 assembly

**Statement:** A semantically accepted program can be lowered, translated and serialized for a
selected platform.
**Evidence:** codegen/compiler integration and golden tests.
**Confidence:** ✅ Confirmed.

### LANG-03: Memory intrinsics accept only literal addresses in current lowering

**Statement:** `peek`, `poke`, `peekw` and `pokew` reject a variable, parameter or computed address
with `E10045`; only a numeric literal reaches memory lowering.
**Evidence:** `constAddress` and explicit tests asserting variable-address rejection.
**Confidence:** 🔴 Suspicious — conflicts with the frozen `(word, …)` signatures and examples such
as `poke(addr + word(i), value)`.

### LANG-04: One-byte `poke` rejects wide values

**Statement:** A one-byte write accepts byte-compatible values and rejects word-width values before
emission.
**Evidence:** frontend and emit-boundary specification tests.
**Confidence:** ✅ Confirmed — this prevents the former adjacent-address clobber.

## Target Execution

### EXEC-01: Emitted assembly is assembled by ACME

**Statement:** Target programs can be validated for assembler legality and converted into binaries.
**Confidence:** ✅ Confirmed.

### EXEC-02: Selected programs can be executed under VICE

**Statement:** C64 programs can expose runtime state through memory observations and bounded
execution windows.
**Confidence:** ✅ Confirmed.

### EXEC-03: Runtime semantic validation is selective rather than spec-wide

**Statement:** Only specifically authored VICE suites currently receive runtime validation; there
is no systematic rule-to-runtime coverage model.
**Confidence:** ⚠️ Inferred — the observed suite inventory supports it, but “sufficient coverage”
is a product criterion rather than a code fact.

## Evidence and Optimization

### EVID-01: Specification and implementation tests use distinct filename tiers

**Statement:** Normative tests use `*.spec.test.ts`; implementation-shape tests use
`*.impl.test.ts`.
**Confidence:** ✅ Confirmed by repository policy and test inventory.

### EVID-02: Assembly twins compare selected compiler output with hand-authored output

**Statement:** A parity corpus records byte and static instruction-cost divergence for selected
pairs.
**Confidence:** ✅ Confirmed.

### EVID-03: Aggregate “cycles” are static instruction-cost sums

**Statement:** The scoreboard sums each emitted instruction's maximum cost once rather than
measuring execution frequency.
**Confidence:** 🔴 Suspicious when interpreted as runtime performance; valid only as a static proxy.

### EVID-04: Example-led development is used as readiness evidence

**Statement:** Slices and demos provide regression and parity evidence, but most were authored
within current compiler constraints.
**Confidence:** 🔴 Suspicious as a readiness baseline because it can omit unsupported language
forms by construction.
