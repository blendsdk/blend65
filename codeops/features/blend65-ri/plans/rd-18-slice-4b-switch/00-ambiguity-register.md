# RD-18 Slice 4b — Ambiguity Register

> **Plan**: rd-18-slice-4b-switch
> **Status**: ✅ **GATE PASSED** — all items Resolved with the user's explicit decisions (2026-07-07)
> **CodeOps Skills Version**: 3.2.0
> **Header**: AR-1 … AR-14

The Zero-Ambiguity Gate register for Slice 4b (the `switch`/`case`/`default`/`fallthrough`
sub-machine — deferred from Slice 4a by AR-1). Every plan item traces to a numbered decision below.
AR-1…AR-4 are the four gate decisions the user made on 2026-07-07 (the "pick the best option"
delegation); AR-5…AR-14 are grounded design/scope resolutions established by the three-agent
current-state recon (2026-07-07) and confirmed as part of the complete-register confirmation.

> **Diagnostic-code precedent (inherited from Slice 3b AR-11 / Slice 4a).** The **actual registry**
> `packages/core/src/diagnostics/diagnostic-codes.ts` is the operative source of truth, and it
> follows **spec Ch 14** (the diagnostics registry) NOT the internally-inconsistent **Ch 05**
> (language chapter) where they conflict. New codes are minted **additively into the registry only**
> (`spec/` frozen, D3), with the Ch-14 drift recorded as an accepted deviation (RD-18 AR-115). Where
> a Ch-05 number is *free* in the registry and does not collide with Ch 14, Slice 4b reuses it to
> *reduce* drift. The spec has **two conflicting switch numbering schemes** — Ch 05/F009/index's
> `E10070–E10076` band vs. the Ch 14 registry's `E10130–E10133` band; the registry (already carrying
> `E10130`/`E10132`/`E10133`) is authoritative. `E10132`/`E10133` also collide with F015 data-inclusion
> in the feature index — irrelevant here because the registry keeps F015 in `E10200–E10204`.

| **AR-1** | Codegen strategy | Lower switch dispatch as a `brcond` compare-chain, or as a jump table? | **`brcond` compare-chain.** Lower each case value as a `CMP` + conditional branch, chained — reuses the Slice-4a `br`/`brcond` multi-block CFG keystone with **zero** new IL terminators and **zero** new `translate.ts` work (the IL terminator set `br`/`brcond`/`ret`/`unreachable` in `instruction.ts:156-165` suffices). Matches RD-18's committed "correctness first, optimizers → Phase B" (AR-111): a jump table is a density/speed **optimization** requiring a new `ILTerminator` variant + translate arm + bounds-check + table emission — deferred to Phase B. | ✅ Resolved (user) |
| **AR-2** | Scope / operand types | Does 4b handle enum-typed switches + enum exhaustiveness (E10133), or integer switches only? | **Integer-only.** 4b handles `byte`/`sbyte`/`word`/`sword` discriminants; `boolean`/other invalid operands → **E10075**. Enum-typed switches + **exhaustiveness (E10133 `NonExhaustiveSwitch`)** defer to **Slice 7** (aggregates), where enum *types* first exist in the type system — 4b literally cannot type-check an enum switch yet. This also matches the spec: F009 lists enum-exhaustiveness as a **future** feature (`F009:558`); Ch 05 §8 imposes no exhaustiveness rule. `E10133` stays registered-but-unwired until Slice 7. | ✅ Resolved (user) |
| **AR-3** | Diagnostic codes | `fallthrough` in a `default` clause: the spec (F009) calls it a warning, the stale RD-18 Parked-Q4 note assumed a new **error** code. Which? | **Spec-aligned `E10073` warning — no new code (Parked-Q4 dissolved).** Per spec §8.3 + `F009:110-112`, `default` is the **last** clause, so a `fallthrough` there "has nothing to fall through to" = the **same `E10073` warning** as a `fallthrough` in the last case. The spec is authoritative (Language Guard). The Parked-Q4 assumption (a new hard error) predates re-reading F009, and its tentative "`E10134`" is now spent on 4a's `NonBooleanCondition` anyway. `E10073` (`FallthroughNoEffect`) covers **both** last-case and default. | ✅ Resolved (user) |
| **AR-4** | Diagnostic codes | Spec assigns `E10072` to "case value type ≠ switch expression type", but `E10072` is already taken by the parser's `MissingDefaultClause` (RD-03). Where does the case-type-mismatch check emit? | **Mint a new dedicated code in the free switch band: `CaseValueTypeMismatch: "E10077"`** — additively into `diagnostic-codes.ts` per the AR-11/AR-115 precedent (`spec/` frozen; Ch-14 drift = accepted deviation). `E10077` is free in the registry/spec/code, adjacent to the switch band, no Ch-14 collision. Distinct, switch-specific message beats reusing the assignment-flavored `E10153`/`E10154`. Language-Guard-approved at this gate. Message: `Case value type '<case_type>' does not match switch expression type '<switch_type>'`. | ✅ Resolved (user) |
| **AR-5** | Scope / spec divergence | The parser (RD-03) **requires** `default` — its absence emits `E10072 MissingDefaultClause` and synthesizes an empty `DefaultClause` (`parse-stmt.ts:276,303-309`). Spec §8.7 says `default` is **optional**. Reconcile in 4b? | **No — out of 4b scope; keep RD-03's shipped behavior.** "default required" is a deliberate, shipped, test-covered RD-03 parser decision (stricter than the spec), and it is the "E10072 collision" AR-1-of-4a named. 4b is a **semantics + codegen** slice, not a parser reconciliation. Consequences accepted: (a) every 4b switch — fixtures included — carries a `default`; (b) `defaultClause` is always non-null, so lowering may rely on it. The spec-vs-impl divergence is recorded here as a known deviation; a parser reconciliation, if ever wanted, is a separate task. | ✅ Resolved (grounded) |
| **AR-6** | Semantics / break-continue | Does `break`/`continue` inside a `switch` break the switch (C model) or pass through to the enclosing loop (spec's Swift/Rust model)? | **Transparent to switch (spec §9).** `05-...:461`: "`break` does **not** apply to `switch` (switch uses auto-break)"; `F009:117,126-129`: `break`/`continue` **pass through** to the enclosing loop. So switch lowering pushes **no** break/continue context; a `break`/`continue` inside a switch targets the enclosing loop's existing 4a `LoopContext`, and a `break` inside a switch with **no** enclosing loop is still `E10130` (unchanged 4a `loopDepth` check — being in a switch does **not** raise `loopDepth`). The registry name `BreakOutsideLoopSwitch` is a Ch-14 artifact; the operative rule is spec §9. | ✅ Resolved (grounded — spec) |
| **AR-7** | Scope / validators | Which switch validators does 4b enforce (integer subset)? | **The integer-switch core set:** case value compile-time-constant (**E10071**); case-value type-match (**E10077**, AR-4); duplicate case value across multi-value lists (**E10132** — wire the registered code); invalid switch-operand type (**E10075**, AR-2); at-most-one `default` (**E10076**); `fallthrough` no-effect in last clause/default (**E10073** warning, AR-3); `fallthrough` position — must be the last statement of a case body and not inside a nested block (**E10074**). **Deferred:** exhaustiveness **E10133** (→ Slice 7 with enums, AR-2). Duplicate-case is `E10132` (registry) not `E10070` (Ch-05) per the precedent header. | ✅ Resolved (grounded) |
| **AR-8** | Codegen / multi-value | How is a multi-value case (`case 1, 2, 3:`) dispatched? | Each value in `CaseClauseNode.values` gets its **own** `eq` compare + `brcond` to the **shared** case-body block; a match on **any** value enters the body. Emitted in source order; the body block is reserved once and targeted by every value's true-edge. Duplicate values (within or across cases) are rejected at semantics (E10132, AR-7) before lowering. | ✅ Resolved (grounded) |
| **AR-9** | Codegen / fallthrough | How does `fallthrough` change a case body's terminator? | A case body **without** a trailing `fallthrough` terminates with `br(join)` (auto-break — the Swift/Rust default, spec §8.2). A case body **with** a trailing `fallthrough` terminates with `br(<next clause's body block>)` — control falls into the next clause's **body**, skipping its case tests (`F009:111`, "always the next case in source order"). `fallthrough` into `default` is the same fall-into-next-body edge (default is the next/last clause). `fallthrough` in the last clause has no next body → `E10073` warning (AR-3) and terminates with `br(join)`. | ✅ Resolved (grounded) |
| **AR-10** | Const-eval | Does 4b need to extend the const-evaluator for case labels? | **No.** The 3b/4a `evalConst` already folds `NumericLit`/`BoolLit`/unary `±`/binary `+ - * / %`/`lo`/`hi` — sufficient for integer case labels (incl. `MAX+1`, `3*4`). A **non-const** case value → **E10071** (AR-7). Enum-member case labels (`Direction.UP`) are out of scope with enums (AR-2). | ✅ Resolved (grounded) |
| **AR-11** | Semantics / dispatch site | Where do the switch semantics attach? | `type-check/statement-typing.ts` currently **skips** `SwitchStmt` at its dispatch `default:` arm (`:138-141`, comment "switch/const/error — out of the 4a surface"). Add a `case "SwitchStmt":` there: type the discriminant (operand-type check E10075), type + const-fold each `CaseClauseNode.values` (E10071/E10077), run duplicate detection (E10132), enforce at-most-one-default (E10076) + `fallthrough` position (E10073/E10074), and recurse each clause `body` via the existing body-typing path. No change to `passes.ts`. | ✅ Resolved (grounded) |
| **AR-12** | Semantics / locals | Case/default bodies can declare `let` locals — are they collected? | **Yes — flat into the function scope (mirror 4a AR-9).** `function-collection.ts`'s `collectStmtLocals` skips `SwitchStmt` at its `default:` arm (`:165-168`). Add a `SwitchStmt` arm recursing `cases[].body` + `defaultClause.body` (mirroring the `IfStmt`/`ForStmt` recursion at `:142-164`), collecting nested `let` locals into the enclosing **function** scope so each gets an SFA frame slot. Real block-scope lifetime is deferred with 4a AR-2/AR-9. | ✅ Resolved (grounded) |
| **AR-13** | Acceptance | The 3-part-bar fixture + observable outcome for 4b. | `examples/slice4b/main.blend`: `main` switches on a module `byte` selector, with a **multi-value** case, a `fallthrough`, a plain (auto-break) case, and a `default`, computing a deterministic `byte` result `poke`d to `$C000`. VICE asserts `$C000 == <computed>`. Exact program + value fixed in `03-03-acceptance-fixtures.md`. Golden of the emitted ASM committed (`slice4b.asm.golden`). Negatives (via `compile()`, no binary): a non-const case value → **E10071**; a duplicate case value → **E10132**; a `boolean` switch → **E10075**. Dispatch correctness depends on the 4a **DEF-1** `eq` fix (compare-chain uses `eq`). | ✅ Resolved (grounded) |
| **AR-14** | Rollout | Which parent items does 4b advance, and does it close RD-18 AC-3? | 4b **closes RD-18 AC-3** (Slice 4 = the full control-flow surface: 4a conditionals/loops + 4b switch) → flip AC-3 `[~]`→`[x]`.
