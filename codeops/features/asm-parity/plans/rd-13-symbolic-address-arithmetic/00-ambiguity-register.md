> **CodeOps Skills Version**: 3.11.0

Numbering continues the feature-wide sequence (RD-stage items 78–82 and preflight runtime items
83–87 live in [`requirements/00-ambiguity-register.md`](../../requirements/00-ambiguity-register.md))
so a single `AR #n` is unambiguous across asm-parity.

**Imported pre-resolved** from the RD stage and its preflight, not re-litigated here: the M1/M2/M3
scope split; the exclusion of `hi(&X) * 4` from the fold; the exclusion of `const` declarations
naming link-time addresses (spec-blocked under D3); `hi(&X / 2^k)` and the word-context forms
keeping their current paths; the deliberate absence of an offset field on the new instruction
operand; the re-routing of 16 divergence rows to
[#70](https://github.com/blendsdk/blend65/issues/70); and `W10172` being left producer-less with
[#71](https://github.com/blendsdk/blend65/issues/71) as its owner.

## Decisions surfaced during authoring and preflight

| # | Category | Ambiguity | Options | Decision | Status |
|---|----------|-----------|---------|----------|--------|
| 96 | Scope (runtime) | `examples/boing-ball` was committed after the plan was written and carries the same idiom at `main.blend:54` — `let base: byte = hi(&BALL) * 4;`, a **`let` initializer** rather than a `poke` value. AC-6 and Phase 4 named only `balloon` and `balloon-color`, so the repo's newest demo would be left teaching the idiom this RD retires | (a) Migrate all three / (b) Leave `boing-ball` on `hi(&X) * 4` — it still gets M1's speedup for free | ✅ Resolved — User accepted recommendation: **(a)**. `boing-ball` is the strongest case of the three: its ball is four consecutive 64-byte blocks addressed as `base+0..3`, so the program is already doing 64-byte block arithmetic while naming the first block through a page-alignment identity that holds only by luck — and it is the example RD-15's 64-byte alignment breaks first, since `hi(&X) * 4` computes the wrong block the moment the image is no longer page-aligned. Phase 4 grows by 2 tasks (50 → 52) | ✅ Resolved |
| 97 | Scope (preflight) | An address byte used as an **array index**. The plan excluded `indexIntoX` from the new operand on the grounds that "an address byte as an array index has no meaning" — but `table[lo(&X)]` **compiles today** (measured: 19 bytes, the index homed through a word slot and reloaded), so after M1 the exclusion turns a working program into an `E90001`, contradicting this plan's own "no program that builds today stops building" | (a) Give `indexIntoX` an `addrByte` arm mirroring its `isImmediate` arm / (b) Keep the exclusion and delete the compatibility guarantee | ✅ Resolved — User accepted recommendation: **(a)**. The premise was wrong: an address byte is an ordinary byte, and a block number indexing a frame table is exactly the idiom this project serves. The exclusion was also inconsistent by accident — a word-element array already works through `scaleIndex` → `mul` → `leftIntoA`, and a >256-byte array through the `byteRefOf` zero-extension recursion; only the commonest case, a small byte array, would have ICEd. One arm, and the largest single win in the RD: **19 bytes → 8**, `LDX #<sym` · `LDA table,X` · `STA $D020` — the hand idiom exactly. Prime Directive: *a restriction that forces un-idiomatic user code is itself the bug* | ✅ Resolved |
| 98 | Testing (preflight) | ST-13j promised a **build-only** test asserting the assembled bytes at `$07F8`–`$07FB` equal `b, b+1, b+2, b+3`. Those bytes do not exist in the PRG: `boing-ball` computes all four at runtime from an animating `frame` (`main.blend:94-99`), and `$07F8`–`$07FB` are VIC pointer RAM outside the load image | (a) Split the criterion — the link-time half in CI, the memory half in the local VICE tier / (b) Move the whole assertion to VICE / (c) Drop the sibling-pointer row | ✅ Resolved — User accepted recommendation: **(a)**. The property RD-15 depends on — that the migrated value is still usable as a 64-byte block base — *is* provable in CI, just not as memory bytes: the `base` initializer's assembled immediate against the symbol map, plus the `ADC #1/#2/#3` → `STA $07F9..$07FB` chain. (b) would reduce boing-ball's CI evidence to "it assembles"; (c) would delete the one assertion neither balloon carries | ✅ Resolved |

| 99 | Architecture (preflight) | A byte-select in any **`materialise` position**. Every non-store expression position wraps its lowered value through `materialise` (`lower.ts:2659-2666`), which passes temps through but wraps everything else in `{ op: "const", … }` — and `translateConst` (`translate.ts:655-658`) ICEs on a non-immediate source. Today `emitLo`/`emitHi` return a *temp*, so it passes; after M1 they return a bare `addrByte` and every one of the **ten** `materialise` call sites regresses. Measured: `let b: byte = lo(&X);` and `v = hi(&X);` both compile today | (a) One `isAddrByte` arm on `translateConst` / (b) Make `materialise` pass `addrByte` through like a temp / (c) Narrow M1 to store positions only | ✅ Resolved — User accepted recommendation: **(a)**. `materialise` is a single funnel and `translateConst` is the sole consumer of `const`, so one byte-only arm covers all ten positions at once, and the emission is optimal — `LDA #<(sym / 64)` · `STA base`, 5 bytes, because the following store folds through `leftIntoA`'s register suppression. (b) yields the same bytes but widens where a raw `addrByte` can appear — conditional-slot stores, `store_indexed` values, the coercion path — each then owing the audit 03-01 §5 just did. (c) would keep `boing-ball`'s `let base` on the 18-byte homing path, forfeiting AC-6's third migration and ST-13j's oracle with it. **This was the blind spot both preflight iterations shared**: §5 audited the *translate-side* consumers of the new operand exhaustively and never audited the *lowering-side* positions that wrap a result in `const` — one of which is the exact line task 4.7 writes | ✅ Resolved |

| 100 | Dependency (runtime) | M1 shrinks `balloon` by 11 bytes, so the sprite's `!align 256` padding grows from 6 to **17** bytes. At 9+ bytes ACME truncates the report's byte column with a literal `...`, and the column then exactly fills its field — so for a **column-zero** directive there is no whitespace before the source text: `139  08ef 0000000000000000...!align 255, 0, 0`. `parseReportFile` (`packages/compiler/src/acme/report-file.ts:130`) splits columns on whitespace, swallows `...!align` as the bytes token and throws, which fails the `balloon` budget tier. A **pre-existing** parser defect, not a budget breach: only `balloon` emits `!align`, and its padding had never crossed 8 bytes. Fixing it lies outside the RD's stated scope but blocks Phase 2 | (a) Anchor `ADDRESSED_LINE`'s bytes column on its real grammar — hex pairs plus an optional `...` — and add a regression spec test / (b) Same fix, no test, relying on the budget tier / (c) Land the fix as its own commit ahead of Phase 2 | ✅ Resolved — User accepted recommendation: **(a)**. Verified against the real report before deciding: the new pattern differs on **exactly 1 of 147** lines — the broken one — and is byte-identical on every other, so it is a column-split correction rather than a behaviour change. The test matters because the trigger is a *size coincidence*: Phase 4 shrinks `balloon` again and may well drop the padding back under 9 bytes, at which point the budget tier stops covering this and the defect returns silently on the next program that aligns. Indenting `!align` so a space always separates the columns was rejected — it is a deliberate column-zero directive (`print-instr.ts:194`) and moving emitted text for a parser's convenience is backwards | ✅ Resolved |
