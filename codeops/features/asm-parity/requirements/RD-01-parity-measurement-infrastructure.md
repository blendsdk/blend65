## Feature Overview

The Prime Directive (project `CLAUDE.md`) judges every compiler change by output parity with
hand-written 6502 assembly — but today nothing in the toolchain *measures* that parity. The
test harness asserts memory states (correctness), never cost: the VICE driver has no cycle
measurement, the resource report stops at segment sizes, no per-instruction 6502 timing table
exists anywhere in the repo, and CI has no size or budget gate. "As good as hand-written"
is currently a vibe, not a gate.

This RD builds the instruments: measured cycle counts in the emulator harness, a shared 6502
timing table, byte/cycle budget assertions that ratchet, a golden↔twin diff tool with a parity
ratio, CI size-regression failure, a static cycle annotator, and per-function cycle estimates
in the compiler's resource report. Every subsequent sweep (RD-09…RD-14) and optimization RD
(RD-04…RD-07) relies on these numbers; RD-02's scoreboard is generated by the tooling shipped
here.

**Affected packages**: `@blend65/core` (timing table, report types), `@blend65/test-harness`
(measureCycles, budget tier), `@blend65/compiler` + `@blend65/cli` (report integration),
`scripts/` (twin-diff, annotator), `.github/workflows/ci.yml` (budget tier already runs via
`yarn test`; ACME is installed there today).

## Functional Requirements

### Must Have

- [ ] **F1 — Timing table** *(complexity: M)*: `@blend65/core` exports a `timing/` module
  covering every documented NMOS 6502 opcode: mnemonic, addressing mode, byte size, base
  cycles, page-cross penalty, and branch penalties (taken +1, taken-across-page +2). The table
  is keyed by the existing `instr-model` types (`Opcode`, `AddressingMode`), with the opcode
  key narrowed to an NMOS subset type so an out-of-table opcode fails at compile time.
  > **Decision per AR #6:** table lives in `@blend65/core` (R15-safe, one table for all consumers).
  > **Per preflight PF-002/PF-006:** NMOS-scoped (65C02 timing is named future work — see Won't
  > Have); keyed by `instr-model` types; coverage cross-checked against the codegen legality table (AC-2).
- [ ] **F2 — Measured cycle counts** *(complexity: L)*: `@blend65/test-harness` exports
  `measureCycles(driver, symbols, fromLabel, toLabel)` returning the exact number of CPU cycles executed
  between arrival at `fromLabel` and arrival at `toLabel`, including any IRQ-handler cycles
  inside the window; identical binaries produce identical measurements across runs.
  > **Decision per AR #2:** contract as stated; per-frame loop measurement is expressed via label
  > placement — no separate API. **Per AR #1 (deferred):** the VICE mechanism (counter command
  > vs. raster arithmetic vs. single-step) is chosen at make_plan after a protocol spike against
  > VICE 3.10; the plan may not pick one silently. **Per preflight PF-004:** the signature
  > carries the symbols map — labels resolve exactly as in `runUntilLabel` (AR #13 addendum).
- [ ] **F3 — Budget assertions** *(complexity: M)*: a budget tier
  (`packages/test-harness/src/budgets.spec.test.ts`) asserts, per fixture, assembled binary
  byte size and named cycle windows against `packages/test-harness/test/golden/budgets.json`.
  Static budgets (bytes + straight-line cycle estimates) assert in CI; measured-cycle budgets
  assert in the local `skipIf(!hasVice())` tier. Initial budgets are set to current values
  exactly (ratchet). The tier covers the golden fixtures **plus the balloon example build**,
  compiled from `examples/balloon/main.blend` through the real compiler (the same build path
  twin-diff uses). Initial coverage: the `slice8b` copy inner loop (static + measured); a new
  minimal **raster-poll golden fixture** (the poll idiom as a first-class golden; its twin is
  RD-02's); and the balloon build — its poll loop asserts a **static per-iteration** budget in
  CI, and its **measured** window sits on the phase-stable frame-update body (poll-exit →
  next poll-entry), because a busy-wait's measured total tracks raster arrival phase, not code
  cost.
  > **Decisions per AR #3 (single budgets.json), AR #5 (CI/local split), AR #12 (exact ratchet).**
  > **Per preflight PF-001** (raster window home: balloon build + new golden fixture) **and
  > PF-003** (poll loops budget statically per-iteration; measured ratchets live on phase-stable windows).
- [ ] **F4 — Size-regression gate** *(complexity: S)*: growth of a golden's assembled binary
  beyond its recorded byte budget fails CI (realized by F3's byte assertions — ACME is present
  in CI); unblocking requires a deliberate `budgets.json` update in the same change.
  > **Decision per AR #4:** hard-fail, no advisory mode.
- [ ] **F5 — Twin-diff tooling** *(complexity: M)*: `scripts/twin-diff.mjs` (alias
  `yarn twin:diff`) diffs each golden↔twin pair from a pair manifest, categorizes every
  divergence into: instruction selection, layout, data placement, addressing modes, register
  usage; and reports parity ratios (generated ÷ hand-written) for bytes and straight-line
  cycles, 1.00 = parity. Markdown to stdout, optional JSON file output. Runs locally and as an
  informational (non-failing) CI step.
  > **Decisions per AR #9 (ratio + taxonomy), AR #10 (`<fixture>.twin.asm` beside goldens;
  > `examples/balloon/balloon.asm` stays put, registered in the manifest), AR #11 (output form;
  > the committed scoreboard document is RD-02's deliverable).**
- [ ] **F6 — Static cycle annotator** *(complexity: M)*: `scripts/annotate-cycles.mjs` (alias
  `yarn annotate:cycles`) reads an ACME report file and emits the listing annotated with
  per-instruction cycle counts (min/max where variable; page-cross determined exactly from
  final addresses) and per-block sums (block = label or branch boundary).
  > **Decision per AR #8:** ACME report input; a convenience flag assembles a `.asm` first.
- [ ] **F7 — Resource-report integration** *(complexity: M)*: `ResourceReport` gains
  per-function straight-line cycle estimates (min–max; each instruction counted once; loops not
  multiplied; labeled as straight-line in output) plus per-function byte sizes, rendered in
  both the terminal build summary and `--report json` / `--emit-report`. When the build's CPU
  variant is not NMOS 6502 (today: Commander X16, `wdc65c02`), cycle-estimate columns are
  omitted with an explicit "no timing data for this CPU variant" label; byte sizes remain.
  > **Decision per AR #7:** straight-line min–max; loop-aware totals are out of scope.
  > **Per preflight PF-002:** NMOS-only table + explicit graceful degradation for other variants.

### Should Have

- [ ] **F8 — `startupCycles` population** *(complexity: S)*: the C64 platform startup routine's
  cycle cost is computed via the timing table and populates the existing
  `ResourceReport.startupCycles` field (the terminal renderer already prints the line).
  > **Decision per AR #14.**
- [ ] **F9 — Annotator convenience assemble** *(complexity: S)*: `yarn annotate:cycles` accepts
  a `.asm` source and invokes ACME with report output itself when given the flag (AR #8).

### Won't Have (Out of Scope)

- Authoring the missing hand-written twins (including the new raster-poll fixture's) — RD-02
  (this RD ships the tooling; the only existing pair is balloon).
- A committed scoreboard document / publication cadence — RD-02 (AR #11).
- Loop-aware cycle totals (iteration-count analysis) — statically infeasible (AR #7).
- Populating `peepholeStats` — belongs to the optimizer work (blend65-ri/RD-08; seeded by RD-06).
- Replacing the `INSTRUCTIONS_PER_FRAME` heuristic in `runFrames` with cycle-exact frame
  stepping — a separate harness refinement; F2 may inform it but does not include it.
- Undocumented/illegal opcode timings — the emitter only produces documented opcodes.
- 65C02 (`wdc65c02`) timing data — the table is NMOS-scoped; non-NMOS builds omit cycle
  estimates with an explicit label (F7). 65C02 timings land when X16 parity work begins
  (preflight PF-002).
- Cross-validating the intrinsic catalog's hand-stated `costMetadata` against the timing
  table — a natural later enrichment alongside the optimizer work (preflight PF-008).

## Technical Requirements

### Timing table (`@blend65/core` → `timing/`)

Pure data + lookup functions, no I/O. Keyed by the existing `instr-model` types — conceptual
record per legal (`Opcode`, `AddressingMode`) pair:
`{ bytes, baseCycles, pageCrossPenalty, branchTakenPenalty }`, with the opcode key narrowed to
an NMOS subset type (out-of-table opcodes fail at compile time). Source of truth:
documented NMOS 6502 timings (as in the WDC/MOS datasheets and the VICE source); coverage is
cross-checked against the codegen NMOS legality table (AC-2). Consumed by
F3 (budget estimates), F5/F6 (scripts import the built package or a generated JSON mirror —
plan decides the wiring), F7/F8 (report). Spec tests pin reference values (see AC-2).

### `measureCycles` (`@blend65/test-harness`)

Sits beside the existing run strategies (`run/strategies.ts`) and follows their conventions:
signature `measureCycles(driver, symbols, fromLabel, toLabel, timeout?)`, timeout-guarded via
`withTimeout`, labels resolved through the same symbols map `runUntilLabel` uses. Semantics per AR #2.
Mechanism deferred per AR #1 — candidate mechanisms for the plan spike: a binary-monitor cycle
counter if VICE 3.10 exposes one; raster-position (LIN/CYC) arithmetic + frame counting;
single-step counting via `ADVANCE_INSTRUCTIONS` + the timing table.

### Budget file (`test/golden/budgets.json`)

One JSON document, all budgeted programs (golden fixtures + the balloon build). Conceptual
shape per program: assembled binary byte budget, plus named cycle windows
`{ name, fromLabel, toLabel, staticMaxCycles?, measuredMaxCycles? }` (busy-wait windows carry
static per-iteration budgets — representation is a plan-level detail).
Exact schema is a plan-level detail; the file is data (not code) so tooling — the budget tier,
the twin-diff scoreboard — can read it. Malformed budget files fail loudly with a clear error.

### Twin-diff pair manifest

The manifest maps golden → twin: the goldens in `packages/test-harness/test/golden/` (the 12
existing plus the raster-poll fixture) pair with `<fixture>.twin.asm` siblings (authored by
RD-02), and the balloon pair maps generated balloon output to `examples/balloon/balloon.asm`
(AR #10). The generated balloon side is never committed: the tool produces it at run time by
compiling `examples/balloon/main.blend` through the built compiler into a temp/build location
(the budget tier shares this build path). Missing twins are reported as
"unpaired", never as errors — the tool must be useful from day one with a single pair.

### Resource report

Extends `ResourceReport` (`packages/core/src/report/resource-report.ts`) with a per-function
section; today the report is segment-level only, so codegen must surface per-function
instruction data to the report builder (`build-resource-report.ts`). Both renderers
(`render-report-terminal.ts`, `render-report-json.ts`) present the new section; the existing
terminal-render golden is updated in the same change.

## Security Considerations

- **Data sensitivity**: none — all inputs are repo-local source/listing files and emulator
  state; no PII, credentials, or user data.
- **Input validation**: `twin-diff.mjs` and `annotate-cycles.mjs` canonicalize input paths and
  reject paths resolving outside the repository root (no `..` traversal); malformed
  `budgets.json` / manifest / ACME report input fails with a clear error before any output is
  written (matching the fail-loudly pattern of `scripts/gen-capability-matrix.mjs`).
- **Injection risks**: scripts spawn ACME/VICE only via argv arrays (never shell
  interpolation), consistent with the existing driver (`buildArgs`); no `eval`, no dynamic
  code from input files.
- **Authentication & authorization / secrets**: none added. The hard-fail choice (AR #4) means
  no PR-comment step, so CI keeps its default minimal `GITHUB_TOKEN` permissions and gains no
  new secrets.
- **Encryption / rate limiting / infrastructure**: N/A — local dev tooling and CI test steps
  only; no network services introduced.
- **Security testing**: spec tests cover path-traversal rejection and malformed-input failure
  for both scripts and the budget-file loader.

## Acceptance Criteria

1. [x] `measureCycles(driver, symbols, fromLabel, toLabel)` is exported from
   `@blend65/test-harness`; for a fixture with labeled window, two consecutive runs of the same
   binary return the same cycle count, and the count includes IRQ cycles when an IRQ fires
   inside the window (demonstrated by a spec test with a raster IRQ enabled — the demonstration
   program may be a hand-written assembly fixture); used by ≥1 `skipIf(!hasVice())` suite.
2. [x] The `@blend65/core` timing module covers all documented NMOS 6502 opcodes; a spec test
   asserts that every legal NMOS (opcode, addressing-mode) pair in the codegen legality table
   has exactly one timing entry; spec tests pin reference values, at minimum: `LDA abs,X` = 4
   cycles +1 on page cross; `STA abs,X` = 5 with no page-cross variance; branches = 2, +1
   taken, +2 taken across a page boundary; `JSR`/`RTS` = 6/6; looking up an opcode outside the
   table is a compile-time (type-level) error, never a silent 0.
3. [x] `packages/test-harness/test/golden/budgets.json` records assembled byte budgets for all
   golden fixtures (the existing 12 plus the new raster-poll fixture) and for the balloon
   build; `budgets.spec.test.ts` fails in CI when any program's assembled size exceeds its
   budget, and the failure message names the program, actual bytes, and budget bytes.
4. [x] Cycle windows exist for: the `slice8b` copy inner loop (static budget asserting in CI
   AND measured budget asserting locally under `skipIf(!hasVice())`); the raster-poll golden
   fixture's poll loop (static per-iteration budget in CI); and the balloon build's
   frame-update body, poll-exit → next poll-entry (static in CI, measured locally). Initial
   values equal current cost exactly (ratchet); lowering any budget below current cost makes
   the corresponding tier fail.
5. [x] `yarn twin:diff` on the balloon pair emits a markdown report where every divergence
   carries exactly one of the five categories (instruction selection, layout, data placement,
   addressing modes, register usage) and byte + static-cycle parity ratios rendered to two
   decimals; `--json <file>` writes the same content as JSON; goldens without twins are listed
   as unpaired with exit code 0; CI runs the script as a non-failing step.
6. [x] `yarn annotate:cycles` on an ACME report of a golden emits every instruction line with
   its cycle count (rendered as `min–max` when page-cross/branch-variable) and per-block sums;
   a spec test verifies a hand-computed reference block, including one page-cross case detected
   from final addresses.
7. [x] Building `examples/balloon/main.blend` prints a per-function section in the build
   summary showing bytes and straight-line `min–max` cycles per function, labeled as
   straight-line estimates; the same data appears under `--report json` and in the
   `--emit-report` file; the terminal-render golden is updated accordingly.
8. [x] (Should Have) `ResourceReport.startupCycles` is populated for the C64 target and the
   build summary's startup line shows a non-zero cycle figure consistent with the timing table.
9. [x] Security requirements verified: spec tests demonstrate both scripts reject a path
   outside the repo root and fail loudly on malformed `budgets.json`/manifest input; no shell
   interpolation appears in any new spawn call.
10. [ ] The full verify command passes (`yarn install --frozen-lockfile && yarn turbo run build
    && yarn turbo run typecheck && yarn turbo run lint && yarn test`), and the area report
    (examined / found / deferred + why) is posted on issue #64 when the RD closes.
